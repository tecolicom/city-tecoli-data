# 公共情報活用のための知識ベース — 設計

作成: 2026-10-23

## 1. これは何か

自治体が web で発信する情報について、**「市民・開発者が実際に使えるか」を領域ごとに実測して評価し、その方法ごと公開する知識ベース**。

二つの顔を持つ。同じデータが

- **使う側**には「どの自治体の、どの情報が、どこから、どれだけの手間で取れるか」の地図になる
- **自治体側**には「現状がどこで、理想がどこで、次に何を直せばいいか」の材料になる

評価は `(自治体 × 情報領域 × 配信元)` の組ごとに付き、**自治体値はそこから導出する** (§5.4、ユーザー判断 2026-10-23)。

### なぜ今か

`japan-gomi-data` で「ごみ収集日」について既にこれをやった。5 軸 100 点の指標 (`docs/opendata-quality-index.md`) を定義し、129 自治体を実測し、解説記事として公開した。その枠組みが**ごみ以外にも効く**ことが分かってきたのが出発点。

直接のきっかけは 2026-10 の経験である。飯能市の新着情報 RSS (`/cgi-bin/feed.php`) が停止したとき、原因を切り分ける過程で近隣自治体を横断比較し、**同一 CMS を使う 4 自治体が同時に停止している**ことを特定した。このとき分かったのは:

- 自治体の web 発信基盤は**少数の CMS 製品に収束している**。同じ製品なら取得口の形も罠も同じ
- つまり**代表を 1 つ調べれば群全体に展開できる**。一人で全国 1,786 自治体を個別調査する必要はない
- そして**「今日取れた」は「明日も取れる」の根拠にならない**。静的データの評価軸では、この性質が落ちる

### 誰が使うか

**自治体職員でも開発者でもない人が、LLM を使って自分の街の情報を整理できること**を目標に置く。人が読んで分かることも重要だが、**機械可読性と LLM からの操作性を優先する**。

これは「一人で全国をカバーするのは不可能」という前提から来ている。本知識ベースは完成品のデータセットではなく、**各自治体や住民が自分の街ぶんを足していける土台**として作る。`japan-gomi-data` の `CONTRIBUTING.md` / `AGENTS.md` と同じ構えを取る。

## 2. ゴール / 非ゴール / アンチゴール

### ゴール

1. `(自治体 × 情報領域)` ごとに、実測に基づく評価を機械可読な形で持つ
2. 評価軸を**既存の国際標準の次元名に対応づけて**定義する (自前の指標を発明しない)
3. **動的コンテンツ (イベント・お知らせ等) の評価**を扱えるようにする。既存枠組みの空白
4. CMS 系統の同定により、少数の実測から多数の自治体を**推定**できるようにする (推定値は推定と明示する)
5. 第三者が LLM を使って自分の自治体ぶんを追加できる手順と schema を提供する
6. 評価が時間とともに変わることを扱う (= パブリックモニタリング)

### 非ゴール

- **全国 1,786 自治体を我々が埋めること。** 土台と種データを作るのが我々の仕事
- **品目辞書のような領域内コンテンツの集約。** それは `japan-gomi-data` のような領域別 repo の仕事。本 repo は「どこに何がどういう形であるか」と「それがどれだけ使えるか」に限る
- **自治体のランキングによる評価・批判。** スコアは改善の材料であって成績表ではない
- **脆弱性の探索。** 公開情報と通常の取得の範囲を超えない (§8)

### アンチゴール (技術的に動いても失敗とみなすもの)

- **自己申告やアンケートに基づく評価。** 既存の国別指標がそこで批判されている (§3)。本件は必ず実測に基づく
- **測っていない値を測った値のように見せること。** 推定・継承・未調査は構造的に区別する
- **人間にしか運用できない形式。** 散文の調査メモだけで schema が無い状態は失敗
- **一度作って腐る静的な調査。** 再実行可能でなければ意味がない

## 3. 前例と位置づけ

### 国際

| 枠組み | 単位 | 測り方 |
|---|---|---|
| **W3C DQV** (Data Quality Vocabulary) | データセット | 語彙のみ提供。測定はしない |
| **ISO/IEC 25012** | データ | 15 次元の分類 |
| **Zaveri et al.** | LOD | 4 カテゴリ (Accessibility / Intrinsic / Contextual / Representational) |
| OECD **OURdata Index** | **国** | 政府への調査。「公開の条件整備」を測り実データは見ない |
| EU **Open Data Maturity** | **国** | 自己申告アンケート 4 次元 (policy / portal / quality / impact) |
| Global Data Barometer, World Bank GovTech | **国** | 調査 |

**空白**: 有力な指標はすべて国単位かつ自己申告。**自治体単位で実際に取得して測る**ものが無い。EU ODM の方法論研究は「Quality 次元の高得点が客観指標と相関しない」と指摘しており、実測ベースの本件はこの批判に直接応える位置にある。また**動的コンテンツの評価を扱う枠組みが無い**。DQV は Timeliness / Availability の語彙を与えるが、測定手法は与えない。

### 日本

| 枠組み | 内容 | 限界 |
|---|---|---|
| デジタル庁 **オープンデータ取組済自治体一覧** | 取組済か否かの**二値**。2025-11-25 更新 | 粒度がゼロ。約 74% が「取組済」 |
| **自治体標準オープンデータセット** (旧 推奨データセット) | 基本編 14 + 応用編 8。項目定義書と CSV 形式つき | 形式の標準であって評価指標ではない |
| 「オープンデータ取組の質評価指標 (ベータ版)」 | 存在の言及のみ確認 | **内容未確認。着手時に追跡すること** |

### 本件の位置

**自治体単位 × 実測 × 動的コンテンツ**。既存指標と競合せず空白を埋める。軸の名前は DQV に寄せることで、国際的な文脈に接続する。

## 4. 全体構造

3 層からなる。**層ごとに設計と実装を切る。全部を一度に作らない。**

| 層 | 内容 | 本設計書の扱い |
|---|---|---|
| **L1 レジストリ** | 自治体ごとの web 発信基盤 (CMS family / 取得口 / 到達性 / 利用条件) | 本書で設計する |
| **L2 評価** | `(自治体 × 領域)` の使えるか評価 | 本書で設計する。最初の領域のみ実装 |
| **L3 手法** | モニタリングの方法論 (差分検知・消滅検知・横断比較・障害切り分け) | 本書では**枠だけ**。別設計書 |

L1 は L2 の A 軸 (取得性) の根拠データであり、同時に L2 を少数調査から推定するための仕組みでもある。

## 5. 評価モデル

### 5.1 領域プロファイル

評価は領域ごとに**プロファイル**を持つ。全領域共通の **5 軸 (コア)** と、領域特性に応じた**追加軸**からなる。

- **コア 5 軸は全領域で同じ定義**。これにより領域をまたいだ横断比較ができる
- 追加軸は領域プロファイルが定義する。横断比較には含めない

`japan-gomi-data` の既存スコアは「静的領域プロファイル (コア 5 軸のみ)」として、**定義を変えずに**この体系に取り込める。既存 129 件のスコアが無効にならないことは要件である。

### 5.2 コア 5 軸 (100 点)

`japan-gomi-data/docs/opendata-quality-index.md` の**軸名・配点・思想を継承**する。

> **「同じ定義」の意味 (設計者判断、2026-10-23)**
> レビューの指摘どおり、ごみの段階表は領域固有の語彙に直結している
> (C 軸は `rules / dates / weekday-rules / partial`、B 軸は `source_type` 列挙、
> キャップ規則は `core_missing = 可燃ごみの日程が無い`)。イベント領域に写像先が無い。
>
> したがって共通にするのは**軸名・配点・思想・由来の扱い (§5.4) だけ**とし、
> **段階表とキャップ規則は領域プロファイルが持つ**。横断比較は軸名と得点のレベルで行う。
>
> **領域非依存の抽象段階表は書かない。** 書けばごみの正典書き換えと 129 件の
> 再採点、既に公表した記事との整合が最初のスライスに入り込む。交換条件が悪い。
>
> **正典の分担**: 新 repo の `docs/index.md` が**コア (軸名・配点・思想・由来・プロファイル規約)**
> を持つ。`japan-gomi-data/docs/opendata-quality-index.md` は**静的領域プロファイルの
> 段階表**として現状のまま残り、コアを参照する。**ごみ側の再採点は行わない。**
> ルーブリックの実装が 2 repo に分かれるとドリフトするため、`score.mjs` は
> コア部分の算出のみを担い、段階表はプロファイル定義から読む設計にする。

| 軸 | 配点 | DQV / ISO 対応 |
|---|---|---|
| A. 取得性 (Access) | 20 | **Availability** (Zaveri ↔ ISO exactMatch) |
| B. 機械可読性 (Format) | 25 | Interoperability / Representational |
| C. 粒度・完全性 (Granularity) | 20 | **Precision** (`dqv:precision`) + Completeness |
| D. ライセンス (License) | 20 | **Licensing** (Zaveri) |
| E. 検証可能性 (Verifiability) | 15 | Traceability / Trustworthiness |

思想も継承する: **「オープンデータとして立派か」ではなく「実際に使えるか」を測る。** 公式カタログに載っていなくても、機械可読で取得できれば得点する。

#### 測定地点 (ユーザー判断、2026-10-23)

A 軸と F 軸の値は**測定地点に依存する**。飯能では商工会議所の REST が国外 IP (GitHub Actions) から 403 を返し、HTML と RSS は通った。

**基準値は国内からの実測とする。** 各値に `observed_from` を持たせ、既定を `jp-residential` とする。

**国外 IP (CI) からの遮断は、スコアではなく family の「到達性の癖」とサイト注記で持つ。** 理由:

- 初回スライスに CI 測定基盤を作らない方針 (§5.3 の G 軸と同じ判断) と整合する
- 利用者の大半は手元の環境から取る。国外基準にすると、国内から普通に取れるデータを低く評価することになる
- §8.1 の「1 自治体あたりのリクエストを最小に」とも両立する

**ただし遮断は「取れない」と等価の実害を生む**ので、注記ではなく**構造化フィールド**として持つこと (`reachability: {overseas_rest: blocked}` 等)。利用側が自動化の可否を判断できる形にする。将来 CI 測定を足す場合は `observed_from: overseas-ci` の値を併置できる schema にしておく。

### 5.3 動的コンテンツ・プロファイルの追加軸

イベント・お知らせのように**継続的に変化する**情報のための追加軸。既存の標準次元に対応づけて定義する。

| 軸 | 対応 | 測るもの |
|---|---|---|
| **F. 更新検知性** | **Timeliness** (Zaveri) ↔ **Currentness** (ISO) | 更新を安く確実に検知できるか。条件付き GET (ETag / Last-Modified) の有無、フィードの有無、更新日時の明示 |
| **G. 継続性** | Availability の時間軸 + Recoverability | 時間を通じて取り続けられるか。観測期間中の可用性、形式変更の頻度と予告、恒久 URL か |

配点は**コア 100 点とは別建て**とし、合算した総合点は作らない。理由: 合算するとコア部分の横断比較が壊れる。表示は「コア 82 / 動的 F:高 G:中」のような併記とする。

> **builder への注記**: F / G の段階定義 (何点が何を意味するか) は本書では確定させていない。ごみの 5 軸が実測 129 件の経験から段差を決めたのと同じく、**最初の領域を 20〜30 自治体実測してから確定させる**こと。先に数字を決めると実態を映さない。

> **G 軸を初回スライスでどう測るか (設計者判断、2026-10-23)**
> G は本来「観測期間中の可用性」なので 1 回の訪問では測れない。しかし L3
> モニタリングは本スライスの範囲外と決めている (§4, §9)。両立させるため、
> **初回は単発訪問で取れる代理指標だけで G を定義する**:
>
> - 恒久 URL か (クエリパラメータ依存・年度別パス・セッション依存の有無)
> - 形式変更の予告の有無 (版表記、`edition` の明示)
> - **既知の障害** — 実地で観測した停止事象。family に記録済みのものを参照する
>
> 時系列の観測 (観測窓・履歴ストア・CI cron・差分検知) は **L3 の設計書で扱う**。
> 初回スライスに CI 基盤を作らない。これにより F/G の段差確定が観測期間ぶん
> 後ろにずれることも避けられる。
>
> **ただし G の定義は L3 で拡張される前提で書くこと** — 代理指標版を `g_proxy`
> のように別名にしておき、後から時系列版を足せる形にする。

### 5.4 評価の単位 — 配信元ごとに持つ

**決定 (ユーザー判断、2026-10-23)**: `assessments/<domain>.yaml` は**配信元ごとに行を持ち**、自治体値はそこから導出する。

理由: ごみでは「一次ソースとして最良のもの 1 つ」で足りた。複数ソースが**同じデータの別表現**だったからである。予定・催事情報は違う。飯能市 1 市で以下の 8 系統が並立し、**中身が重複せず**、取得口の形もライセンスも別である。

| 配信元 | ドメイン | 中身 |
|---|---|---|
| 市のお知らせ (新着 RSS) | `city.hanno.lg.jp` | 市政全般の新着 |
| 市長ブログ | `city.hanno.lg.jp` | 市長の活動 |
| 市民会館 | `city.hanno.lg.jp` | 催事 |
| 議会 | `city.hanno.lg.jp` | 会議日程 |
| 図書館 (本館・こども) | `hanno-lib.jp` | 休館日・イベント |
| 商工会議所 (告知・当番表) | `hanno-cci.or.jp` | セミナー・日替わりシェフ |
| 観光協会 (news・tour) | `hanno-tourism.jp` | 観光イベント・ツアー |

「最良 1 つ」では残りが index から消え、合成すると何の値か分からなくなる。

**非 lg.jp の配信元も対象に含める。** 図書館・商工会議所・観光協会は自治体公式サイトではないが、その街の予定を知るために実際に使われている情報の大半がそこにある。これを外すと「使う側の地図」という目的を外す。

> **builder への注記 (設計者判断)**: `handle` は lg.jp 由来なので非 lg.jp の配信元を指せない。
> 配信元 id は `<handle>/<publisher-slug>` の形を取り、`publisher` レコードに
> `entity_type` (自治体 / 外郭団体 / 商工団体 / 観光協会 / 指定管理者 等)、`domain`、
> `place_id` (あれば) を持たせること。`hanno-data` では既に配信元エンティティ単位に
> カレンダーを割る方向が採られており (図書館で実施済み)、その粒度と揃う。
>
> 自治体値の導出規則 (最良値か、加重か、カバレッジを併せた複合か) は実データを
> 見てから決めること。**導出規則を先に固定しない。**

### 5.5 推定と未調査の区別 (アンチゴール対応)

各軸の値は必ず**由来**を持つ。これは本設計の中核要件である。

| 由来 | 意味 |
|---|---|
| `measured` | その自治体で実際に取得して確認した |
| `inherited` | CMS family の代表実測から継承した。family id と代表 handle を必ず記録 |
| `estimated` | 状況証拠からの推定。根拠を notes に書く |
| `unknown` | 未調査。**0 点ではない。「測っていない」である** |

`japan-gomi-data` が `estimated` フラグで既に部分的にやっていることの一般化。`unknown` を低得点として扱ってはならない — 未調査の自治体が「悪い」ように見えるのは評価として誤りであり、かつ貢献者を遠ざける。

> **どの軸が継承可能か (設計者判断、2026-10-23)**
>
> | 軸 | 継承 | 理由 |
> |---|---|---|
> | A. 取得性 | **可** | CMS が取得口の形を決める |
> | F. 更新検知性 | **可** | 条件付き GET の対応は CMS 実装依存 |
> | G. 継続性 | **可** | 恒久 URL か・障害の出方は CMS/基盤依存 |
> | B. 機械可読性 | **不可** | 中身の形式は自治体の運用が決める |
> | C. 粒度・完全性 | **不可** | 同上。同じ CMS でも書き込む内容が違う |
> | D. ライセンス | **不可** | 自治体ごとの判断 |
>
> **継承した assessment ファイルを機械生成して置くことはしない。**
> family 所属は L1 (`web.yaml`) に持ち、A/F/G の継承は**利用側が導出する**。
> 理由: 埼玉 63 件ぶんを生成すると「中身の大半が推定の index」になり、
> アンチゴール (測っていない値を測ったように見せる) との境界管理が
> 設計の中心作業になってしまう。ゴール 4 (少数実測から多数を推定) は
> 「導出可能な形で持つ」ことで満たす — 実体化は必要条件ではない。
>
> **公開する集計値 (分布・平均) には `measured` のみを含める。** 母数を明示する。

## 6. データモデル

`japan-gomi-data` の構造を踏襲する。既存の運用知識がそのまま使えることを優先する。

```
<repo>/
  docs/
    index.md                   指標の正典 (コア 5 軸 + プロファイル定義)
    playbook.md                新しい自治体・領域を調べる手順書
    monitoring.md              L3 の入口 (別設計書で詳細化)
  schema/
    domains.yaml               情報領域の語彙 (§7)
    family.schema.json
    assessment.schema.json
  families/
    <family-id>.yaml           CMS 系統ごとに 1 件 (§7.2)
  municipalities/
    <都道府県>/<handle>/
      web.yaml                 L1: 基盤 (family / 取得口 / 到達性 / 利用条件)
      assessments/<domain>.yaml  L2: 領域ごとの評価
  scripts/
    fingerprint.mjs            指紋採取 → family 判定
    score.mjs                  評価算出
    validate.mjs
```

- **`handle`** は `city-tecoli-data/municipalities/municipalities.yaml` (全 1,786 件、lg.jp 準拠、CC0) を引く。自前で採番しない
- 公式 URL は現在このレジストリの生成物に含まれていない。`build.mjs` が使う `code4fukui/localgovjp` には在るので、**`website` フィールドを出力に足す**のが前提作業になる
- **未調査でも調査済みなら置く**。`japan-gomi-data` の `survey.yaml` の思想 (「調査済みなら未収録でも置く」) を継承する

## 7. 情報領域の語彙

### 7.1 骨格は国の標準に合わせる

**自治体標準オープンデータセット (基本編 14 + 応用編 8) を骨格**とする。自前で領域を切らない。

**基本編**: AED設置箇所 / 介護サービス事業所 / 医療機関 / 文化財 / 観光施設 / **イベント一覧** / 公衆無線LAN / 公衆トイレ / 消防水利施設 / 指定緊急避難場所 / 地域・年齢別人口 / 公共施設 / 子育て施設 / オープンデータ一覧

**応用編**: 食品等営業許可 / 学校給食献立 / 小中学校通学区域 / ボーリング柱状図 / 都市計画基礎調査 / 調達情報 / **標準的なバス情報フォーマット** / 支援制度情報

これに、標準に無い領域を**拡張**として足す。第一号は **ごみ収集** (標準に含まれない。`japan-gomi-data` が独自 schema を持つ理由)。

**標準がある領域では、評価に「標準形式への適合度」を含められる。** 自治体にとって改善目標が自明になるため、これは本件の価値の中心のひとつ。標準が無い領域では適合度の軸を持たない。

### 7.2 CMS family

L1 の中核。`families/<family-id>.yaml` は以下を持つ:

- **指紋** — 判定規則。URL 構造・特徴的なパス・テンプレート文言・JS ファイル名など
- **取得口のパターン** — 新着フィード等の URL テンプレートと、パラメータの意味
- **系統** — 集合同期型 / 追記型 (`hanno-data` の `adding-a-calendar-source` スキルの判定)
- **到達性の癖** — **国外 IP からの遮断**など。「HTML と RSS は開いたまま REST だけ 403」という形で現れ、ローカルで検証できない
- **既知の障害** — 観測した停止事象。L3 への接続点
- **製品名・バージョン** — 分かれば記録する (§8)

既に一つ、実測済みの family がある。飯能市・日高市・入間市・毛呂山町が共有する系統で、指紋は `/cgi-bin/feed.php?siteNew=1&displayCount=&displayRange=&includeShortcut=` (RSS 1.0/RDF、`dc:date`)、`/index.update.json`、`/news_list.html`、`/theme/base/js/mutual_switching/`、`/resource/js/foot_print.js` (「足あと機能」)、`<!-- CMS編集領域ここから -->`。**製品名は未特定。** 製品名が分からなくても群として同定できれば実用になる、というのが本設計の前提である。

> **builder への注記**: family id は製品名が分からない段階でも振れる必要がある。指紋ハッシュ由来の仮 id (例: `fam-feedphp-sitenew`) を許し、製品名が判明したら別名として足す設計にすること。

## 8. 制約

### 8.1 取得の礼儀 (最重要)

対象は**他者の、それも公共機関のサーバ**である。

- **robots.txt を尊重する。** 指紋採取も例外ではない
- **1 自治体あたりのリクエストを最小に保つ。** 指紋採取はトップページ 1 回を基本とし、family が確定すれば追加取得は要らない設計にする (これが 2 階建てにする理由のひとつでもある)
- **同時実行を絞り、間隔を置く。** 1,786 自治体を一気に舐めない
- **結果をキャッシュし、再実行で再取得しない。** `whois-cache.json` と同じ発想
- **User-Agent に連絡先を入れる。** `hanno-data` の `city.yaml` と同じ規約
- **可用性の測定が負荷になってはならない。** 継続性 (G 軸) の観測頻度は日次を上限とする

### 8.2 脆弱性探索はしない

調査は**公開情報と、通常の利用者が行う取得**の範囲に限る。管理画面のパス探索、既知の脆弱性の試行、認証の試験は行わない。

### 8.3 バージョン情報の扱い

**製品名・バージョンは単なる情報として記録する** (ユーザー判断、2026-10-23)。隠さない。根拠として「調べれば分かること であり、明らかにすることで不用意な自治体が気づく効果の方が大きい」。

ただし**必ず `observed_at` と判定根拠を併記する**。バージョンは陳腐化が速く、根拠のない古い値が事実として一人歩きするのを防ぐため。

### 8.4 ライセンス

`japan-gomi-data` / `city-tecoli-data` に合わせる。**データ (生成物) は CC0 または CC BY 4.0、文書は CC BY 4.0** を想定する。調査対象サイトの本文をそのまま取り込まない (出典の権利と矛盾する)。

## 9. 最初のスライス

**`schedule-events` (予定・催事情報) 領域**から始める。

### 領域の定義 (ユーザー判断、2026-10-23)

**使う側の用途「その街の予定を知る」で領域を切る。** 標準 OD のイベント一覧と、お知らせ・新着フィードを**同じ尺度の上下に並べる**。

| 位置 | 形 |
|---|---|
| 満点形 | 標準 OD「イベント一覧」CSV (自治体標準オープンデータセット 基本編 6) |
| 中位 | 独自形式のイベント一覧 / ICS |
| 下位形 | お知らせ・新着 RSS から拾う (飯能型) |
| 最下位 | HTML ページを読むしかない |

**満点形との差がそのまま改善目標になる。** これが本件の価値の中心である。

> **なぜ分けないか**: レビューの指摘どおり、実測済みの 4 自治体の `feed.php` は
> 「お知らせ」であって「イベント一覧」ではない。`hanno-data` の実装経験も中身は
> 市のお知らせ・市長ブログ・図書館の休館日・商工会議所の告知であり、
> 「市のイベントカレンダー」はそこに無い。
>
> 2 領域に分けると、実測済みの証拠が events 側で使えず、イベント一覧を
> 20〜30 件ゼロから実測することになる。1 領域に統合すれば**既存実測が下位形の
> 証拠として生き、かつ標準への適合度も書ける**。分類の正確さより用途を取る。

理由:

- 動的コンテンツであり、本件固有の貢献 (F / G 軸) が最初から要る
- 国の標準形式があるので、評価がそのまま改善目標になる
- `hanno-data` / `hidaka-data` という実装経験があり、罠が分かっている
- 既に 1 family・4 自治体の実測がある (下位形の証拠として)

### 範囲

| 項目 | 決めたこと |
|---|---|
| 最初の調査対象 | 埼玉県を基本とする。`japan-gomi-data` が埼玉・東京を先行させた前例に合わせ、比較可能性を取る |
| 件数 | F / G 軸の段差を決められる規模 (20〜30 自治体) を下限とする |
| 成果物 | schema + families + 埼玉県ぶんの assessments + 指標の正典 + playbook |

### やらないこと

- 他領域の assessments (schema だけ通しておき、実装はしない)
- L3 モニタリングの実装 (枠だけ)
- 公開ページ・解説記事 (別途)
